# Задание 4. Проектирование продажи ОСАГО

## Принятые решения

### 1. osago-aggregator — отдельный сервис
- Выделен отдельный сервис **osago-aggregator** для отправки заявок в страховые компании и опроса решений по ним.
- Сервис имеет **собственную БД** (osago-aggregator-db) для хранения состояния заявок и полученных предложений.

### 2. Интеграция core-app <-> osago-aggregator: Kafka
- Взаимодействие между core-app и osago-aggregator осуществляется через **Kafka** (Event Streaming).
- core-app публикует заявку на ОСАГО в топик Kafka.
- osago-aggregator потребляет заявку, рассылает её во все страховые компании и по мере получения ответов публикует предложения обратно в Kafka.
- core-app потребляет предложения из Kafka.

### 3. Интеграция Web <-> core-app: WebSocket
- Для отображения предложений в реальном времени (по мере их поступления от каждой страховой компании) используется **WebSocket** между веб-приложением и core-app.
- Это позволяет пушить предложения клиенту сразу, как только они получены, без polling.

### 4. Паттерны отказоустойчивости
- **Timeout** (60 сек) — на вызовы osago-aggregator к страховым компаниям. Макс. время ожидания ответа.
- **Retry** — при временных ошибках osago-aggregator повторяет запросы к страховым компаниям (с exponential backoff).
- **Circuit Breaker** — osago-aggregator применяет Circuit Breaker к каждой страховой компании отдельно, чтобы сбой одной не блокировал остальные.
- **Rate Limiting** — на входящий API core-app от партнёров, для защиты от перегрузки.

### 5. Множественные экземпляры
- Сервисы развёрнуты в нескольких экземплярах. Kafka гарантирует, что каждое сообщение обработается ровно одним экземпляром (consumer group). Состояние заявок хранится в БД, что делает сервис stateless.
